# M7 threads agent: decisions

Rows for docs/DECISIONS.md (Twin Threads and Kindred Flame).

| Date | Question | Decision | Reason |
|---|---|---|---|
| 2026-10-24 | How Twin Threads' fifth slot exists (M7, CONTENT §11) | Every loadout has five slots (`LOADOUT_SLOTS = 5`, src/sim/weave/runtime/slots.ts); the fifth, on R (`Button.Cast5`, bit 1 << 6), is locked unless the hero owns Twin Threads (`slotOpen`, `openSlotCount`). A locked slot refuses every weave ("The fifth weave slot (R) opens with the Twin Threads mutation"); emptying it always works. A weave left in it (a spec, or the mutation taken away by a debug edit) keeps its notation, shows that message as its error, and never fires, like a weave that stopped fitting the spindle | One slot array shape everywhere (saves, replays, hashes, the trigger loop) and one place that decides the lock. The locked slot has no program, so every trigger path (Cast, Channel, Pulse, events, the readout's forcing, `listensFor`) skips it without its own check. |
| 2026-10-24 | What changes for heroes without Twin Threads | Nothing they can see or play: the four slots, their order and priority (the lowest held Cast slot casts first; R is last), the DPS readout (always slot 0) and every test stay the same. The state hash changes once because the slot array has five entries (no golden hashes exist; old replay files already stopped matching with M7's hero.hearth) | The fifth slot only adds an empty entry. |
| 2026-10-24 | Saves with Twin Threads | Saves keep five entries; saves with four (before M7) load with the fifth empty. The save stays version 3 (a longer array is backward compatible). A save whose fifth slot holds a weave but whose hero lacks the mutation loads with it empty, and its runes back in the pouch | Same rule as other invalid weaves in saves (they empty, runes return). |
| 2026-10-24 | Twin Threads in sandbox, arena and the lab | Locked: those heroes own no mutations, and the sandbox's localStorage loadout keeps four slots. Console `weave 5 …` / `weave r …` says "R is locked: …" until the hero has the mutation; then it works like the other slots | The lab already uses R to run stations; a locked slot makes R a no-op in the sim there. The simplest rule is "the hero owns it or not"; in tests, set `hero.hearth.mutations.twin_threads = 1` and call refreshHero. |
| 2026-10-24 | How the UI knows about slot 5 | `getLoadout(session).slots` lists the open slots only (4, or 5 with the mutation; `slots[i].slot === i`). The HUD strip, the Loom's tabs and drafts, the console's `weaves` list and the item-get hints all follow it. `SLOT_LABELS` gains 'R' | One contract for every screen; nothing in the UI checks the mutation itself. |
| 2026-10-24 | Kindred Flame's reading (CONTENT §11) | When fire the player owns newly Ignites an enemy (a hit, an arc, or player-owned burning ground; i.e. applyIgnite takes and its owner is the player), every other live enemy whose body is within 1 cell of it (edge to edge, data/hearth.ts mutationEffects.kindredFlame.reach) and that is Oiled or already Ignited is Ignited too, by the player, for the same duration and the same pre-resistance strength (re-applied through the neighbour's own fire resistance). One hop: a spread doesn't spread again. Wet, immune and already-stronger neighbours are skipped by applyIgnite's own rules. Refreshing an ignite (standing in fire) never spreads | "Fire you create": the owner rule (OWNER.player) already marks the player's fire everywhere. One hop keeps it bounded and deterministic in a single tick (no chain across a packed room), and it costs one pass over the enemies only when an ignite takes. |

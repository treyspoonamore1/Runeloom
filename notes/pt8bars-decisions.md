# Playtest 8: the second weave bar (decisions)

Fen playtest note: "I feel like I kept having to switch elements, but I only have 4 buttons." The designer chose a second weave bar, swapped with X like a weapon swap. These rows record the rules and the ambiguities resolved while building it. Newest last.

| Date | Question | Decision | Reason |
|---|---|---|---|
| 2026-10-27 | How does the player get more weaves without more buttons? | A second weave bar: four more slots on the same LMB, RMB, Q, E buttons, and X swaps which bar is live | The designer chose a second weave bar. |
| 2026-10-27 | Which slot indices do the new slots get? | Slots 0–4 keep their meaning (bar 1 LMB, RMB, Q, E, then R for Twin Threads); slots 5–8 are bar 2's LMB, RMB, Q, E. `LOADOUT_SLOTS` is 9 | Saves, replays and Loom edits from before keep their indices. |
| 2026-10-27 | What state does the bar add? | `WeaveLoadout.activeBar` (0 or 1, hashed and saved) and `swapLeft` (the swap lockout, hashed, not saved) | The designer chose a second weave bar; the lockout is room-scoped like casts. |
| 2026-10-27 | Which bar is R (Twin Threads) on? | Both: R is live on bar 1 and bar 2, and a swap never interrupts it | The designer chose a second weave bar with R shared. |
| 2026-10-27 | Which input swaps, and where? | A new button bit `Button.SwapBar = 1 << 7`, mapped to X (KeyX was unused). The swap runs inside the sim at the start of the trigger phase, on the press edge, so replays reproduce it | The designer chose a second weave bar; input stays plain data through `step`. |
| 2026-10-27 | Can the player swap while dead, frozen or in hitstop? | Not while dead or frozen. A press that lands entirely inside hitstop is lost, as a Dodge press is | Swapping is an action like the others; the simplest rule that matches Dodge. |
| 2026-10-27 | What does a swap interrupt? | An unreleased cast from the bar being left is cancelled ('castCancel'); a released one just ends. Its Channel slots reset their beat timer, as if released. A cast or channel from R goes on | The designer chose a second weave bar. |
| 2026-10-27 | How long until the new bar can act? | `tuning.player.barSwapLockout`, default 0.15 s, in the F2 panel. It counts from the tick after the swap, so the new bar acts on tick T + 60 × lockout (9 ticks). 0 means the swap tick | Feel value; the designer can tune it. |
| 2026-10-27 | What does the lockout block? | Everything on the new bar: casts, channels, Pulse and event triggers. Its timers stay frozen until the lockout ends, so a Pulse waits rather than skipping its beat | One rule ("the new bar is not live yet") instead of separate ones per trigger kind. |
| 2026-10-27 | Can X swap back during the lockout? | Yes; each swap starts a fresh lockout | Simplest; the lockout stops spam casting, not swapping. |
| 2026-10-27 | Which slots act? | Only the live bar's four and R ("acting slots": `weave/runtime/slots.ts` `actingSlots`), for casts, channels, Pulse, queued events, the readout's forced events, `listensFor` and the Channel walking slow | Otherwise a swap could fire everything at once and 8 automatic weaves would be live. The designer chose a second weave bar. |
| 2026-10-27 | Which timers freeze on the inactive bar? | Both trigger timers: Pulse's period and the event triggers' ICD. Nothing else counts down per slot (Cast weaves have no cooldown), so "ordinary cast cooldowns" don't arise | The literal reading of "trigger timers freeze"; an ICD counting down off-bar would only matter for the first event after a swap. |
| 2026-10-27 | Which rune items can a slot socket? | The two bars share the rune pouch: an item can sit in one slot of each bar. For a slot on a bar, the taken items are those in the same bar's other slots, in R, and in the Rune Garden; for R, those in every other slot and the Garden (`slotsClash`) | The designer chose a second weave bar sharing the pouch. |
| 2026-10-27 | What counts as "free" with no slot given (pouch previews, the Garden, salvage)? | An item socketed in any slot is not free; planting or salvaging needs it out of every weave | Simplest; matches what "socketed" meant before. |
| 2026-10-27 | Which runes gain XP from kills? | Only the runes in the live slots (`liveSlots`: the live bar and R, also during the lockout). An item shared by both bars gains once; when it levels, the other bar's weave using it recompiles too | The inactive bar can't level runes passively. The designer chose a second weave bar. |
| 2026-10-27 | Does the save format change? | Yes: version 4. `weaves.notations` and `weaves.runes` hold nine slots and `weaves.activeBar` is new. Migration 3 → 4 changes nothing; parsing fills missing slots empty and the bar with 0. An older build refuses a version 4 save instead of dropping a weave whose item is shared across bars | Saves from before load unchanged; version 4 can hold sharing an older build would reject. |
| 2026-10-27 | How are saved weaves validated? | In slot order, each slot's items must match its runes and not sit in an already accepted clashing slot (same bar or R); a slot that fails loads empty and its items return to the pouch. R without Twin Threads loads empty as before | Same rule as the live game. |
| 2026-10-27 | Do older replays still check? | Yes. The state hash covers bar 2, `activeBar` and the lockout only once any of them is not at its default, so a run that never uses bar 2 hashes exactly as before (checked on all 11 scenarios and an adventure run against the previous commit). Replay files gain an optional `loadout.activeBar` | Replays from before load and match unchanged. |
| 2026-10-27 | How does the HUD show the bars? | The slot row shows the live bar's four slots, then R. Beside it, past a thin divider: the bar number ("1/2"), the other bar's four slots as small greyed glyphs in a 2×2 grid, and an "X swap" keycap. A swap replays a 0.24 s swap-in animation on the row and plays a light two-note sound (`sfx.barSwap`) | The designer chose a second weave bar with the other bar greyed beside it. |
| 2026-10-27 | How does the Loom show both bars? | Slot tabs in two rows, "Bar 1" and "Bar 2" (the live one tagged "live"), each with LMB, RMB, Q, E; R spans both rows at the end. Bar 2 slots are named "Bar 2 LMB" and so on in messages. Up and Down arrows move between the bars | Both bars are editable in one place without a mode switch. |
| 2026-10-27 | How are the Loom's free counts worked out? | For the selected slot: owned copies minus the drafts of that slot, its bar's other slots and R (all slots for R). The other bar's drafts don't count | Rule 4 applied to drafts; the sim's own check on apply stays the source of truth. |
| 2026-10-27 | How does the dev console address bar 2? | `weave <slot> <notation>` takes 6–9 or LMB2, RMB2, Q2, E2 (also 2LMB, bar2:Q) for bar 2. `weaves` lists both bars and ends with the live bar | Extends the existing numbering without a new argument. |
| 2026-10-27 | Where do item-get suggestions go? | To the live bar's slots, then R | The player is using that bar when the rune drops. |
| 2026-10-27 | What do bots, the DPS readout and the sandbox's saved loadout do? | Bots stay on bar 1 (they never press X). The readout worker measures a weave in slot 0 on bar 1, as before (`readoutCharacter` takes the edited slot and follows the bar rule for rune items). The sandbox's localStorage loadout stores all nine slots by index (older four-slot data loads with bar 2 empty); the live bar is not stored there | Keeps every existing consumer unchanged. |
